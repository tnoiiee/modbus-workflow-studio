# Acceptance Test v1.2.11

Status: **approved planning scope; implementation not started**.

This document defines the release gate for Monitor Scheduler & WebSocket Reliability. It does not claim that any test has passed. A row may be marked PASS only after the command, fixture, environment, and evidence are recorded.

## Baseline and existing features under regression

The baseline is v1.2.10 as described in [README.md](../../README.md), [docs/ARCHITECTURE.md](../ARCHITECTURE.md), and [docs/CURRENT_STATE.md](../CURRENT_STATE.md). The acceptance run must preserve:

- React Flow editor, node/edge behavior, dynamic ports, Undo/Redo, Fit View, pan, zoom, MiniMap, and reliable auto-save/revision recovery
- workflow create/rename/duplicate/delete/selection and concurrent isolated workflow sessions
- shared project-level Modbus TCP device connections and per-device queues
- FC01-FC04 reads and FC05/FC06/FC16 writes with zero-based protocol addresses
- `ALLOW_WRITES`, `LIVE_LOCKED`, `LIVE_ARMED`, output ownership conflict protection, write-on-change and read-back guards
- Manual Trigger, logic symbols, Linear Mapping, Runtime Monitor, Traffic Monitor, Audit Viewer and Validation
- read-only Modbus Monitor: lists, Add Item, Add Range, FC01-FC04, READ NOW, continuous monitoring and CSV export

## Approved reliability policy

The implementation must expose typed configuration or diagnostics for the following defaults. The exact configuration mechanism may be finalized during Milestone 0, but changing these defaults requires updating this document before release:

| Policy | Default acceptance value |
| --- | ---: |
| monitor reads in flight per monitor list | 1 |
| pending monitor request per monitor list | 1 |
| monitor queue bound per device | 32 jobs |
| WebSocket outbound queue per client | 256 messages or 1 MiB, whichever is reached first |
| telemetry coalesce window | 100 ms |
| client reconnect backoff | 250 ms minimum, 30 s maximum, with 0–20% jitter |

Monitor work may be coalesced or dropped when stale, but workflow reads, output writes and safety/control state must not be silently dropped because of monitor or telemetry pressure.

## Release and hygiene gates

The following are mandatory release evidence, and must be run after the implementation is complete:

```bash
npm ci --include=optional
npm run check
node scripts/hygiene-check.mjs --all --strict
npm run verify:publish
```

Also required:

- GitHub `Check` and `Hygiene` workflows pass for the implementation commit
- version is synchronized to `1.2.11` in root/client/server, UI/startup/health API, README, CHANGELOG and CURRENT_STATE
- `git ls-files` contains only `data/.gitkeep` and `server/data/.gitkeep` under runtime directories
- no `dist`, `*.tsbuildinfo`, logs, generated workflows, monitor lists, credentials or secrets are tracked
- acceptance evidence identifies every test that was not run; unrun tests must not be described as passed
- release tag and ZIP remain unchanged until all required gates pass

## Known limits and explicit non-claims

This planning document does not claim browser, hardware, long-running load, CI or release results. It does not approve changes to React Flow, workflow runtime semantics, Modbus protocol behavior, output safety, monitor write capability, v1.3.0 published signals or v1.4.0 arbitration.
